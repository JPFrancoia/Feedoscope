# Semantic Freshness

Freshness estimates how long an article's main claim remains useful. Its
expected lifetime drives final relevance-score decay; urgency remains a
separate model.

## Labels

Miniflux has three manual freshness tags:

| Tag | Useful-life range | Representative decay half-life |
|---|---|---:|
| `fresh_d` | 0–29 days | 7 days |
| `fresh_m` | 30 days–6 months | 90 days |
| `fresh_y` | More than 6 months | 365 days |

These representative values are used to calculate an expected lifetime for
relevance decay; they are not hard expiry dates. There are no automatic
freshness tags.

## Training

The bootstrap dataset contains 1,200 labels generated by `gpt-5.6-luna`.
Training combines every bootstrap label with exactly one manual freshness tag
on a read article:

- A read article with one manual tag uses that manual label instead of its
  bootstrap label.
- A read article with conflicting manual freshness tags is excluded and logged.
- Manual freshness tags on unread articles are ignored until the article is
  read.

`make train_freshness` reuses the shared EmbeddingGemma cache and fits two
cumulative `LogisticRegression(C=20, fit_intercept=False)` heads: useful beyond
30 days and useful beyond 6 months. The heads produce three ordered
probabilities, from which the expected lifetime is calculated using 7, 90, and
365 days.

The trainer fingerprints the effective article IDs, labels, sources, and model
configuration. If the active artifact has the same fingerprint, it skips
retraining. The existing Sunday weekly CronJob invokes this command; unchanged
labels therefore do not create a new artifact.

## Weekly evaluation

`make eval` also evaluates Freshness. It uses the older chronological labels for
training and holds out exactly the newest `VALIDATION_SIZE` labels. The results
are stored in the shared evaluation history; see
[Model Evaluation History](model-eval-history.md) for the metrics, Miniflux
schema, and AI Metrics page behavior.

## Inference and relevance decay

`make infer_freshness` is a prediction smoke run. It does not persist freshness
predictions and does not create, update, or link Miniflux tags.

`make full_infer` calculates freshness for active articles in memory, then uses
each valid expected lifetime as the exponential relevance-score half-life. A
missing, non-finite, or non-positive lifetime leaves that article's raw
relevance score unchanged and is logged. Freshness inference likewise does not
persist predictions or write automatic tags.

## Schema

Migration `000006_three_label_freshness` creates the
`freshness_bootstrap_labels` table and the three user-1 tags: `fresh_d`,
`fresh_m`, and `fresh_y`. It does not create inference storage. Miniflux owns
the shared `model_evals` schema and must be migrated before Feedoscope writes
Freshness evaluation rows.

Production is at migration version 6 with `dirty=false`, has 1,200 bootstrap
rows, and has only the three manual freshness tags. The previous
six-label migrations and their automatic-tag/prediction workflow are not
deployed.
